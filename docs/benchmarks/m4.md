# M4 benchmarks: the engine in the browser

**Browser:** headless Chromium 141 (Playwright build 1194) in the same
cloud container as earlier milestones: 4 vCPU Xeon @ 2.1 GHz, 15 GB RAM.
Files are served from localhost by `web/engine-test/serve.mjs`, with COOP
and COEP headers. This is still not the spec's "mid-range laptop", but it
is a real browser running the real WASM builds on the real snapshot.

**Data:** NYC 311 `3b42e46a…`, 7,111,809 rows. `data.arrow` is 497 MB.

**Harness:** `node web/engine-test/browser-bench.mjs <snapshot dir> <chrome> st|mt`.
Each plan runs 3 times and the median is reported. Two full runs per
build are shown as ranges.

## Results

| | `st` (1 thread) | `mt` (4 workers) |
|---|---|---|
| WASM size | 0.78 MB | 1.27 MB |
| Fetch 4 files (localhost) | 1.1 s | 1.1 s |
| **Load + full verification** | **3.2–3.6 s** | **1.65–1.80 s** |
| ↳ decode Arrow IPC | 1.7–2.1 s | 0.96–1.01 s |
| ↳ re-hash every chunk | 1.09–1.18 s | 0.39–0.40 s |
| ↳ sort-order check | 0.05 s | 0.05–0.12 s |
| Validate a plan | 1.7 ms | 1.4 ms |
| Filter one complaint type, count | 263–279 ms | 240–246 ms |
| Noise: median hours by borough | 880–885 ms | 628–692 ms |
| Top complaint types per month (2025) | 634–700 ms | 548–561 ms |
| Full sort of 7.1M rows, first 10 | 5.7–5.8 s | 2.1–2.3 s |
| Trace the Bronx (443,530 rows), cold | 17–20 ms | 10–15 ms |
| Same, cached (includes copying 443k ids to JS) | 7–8 ms | 2–8 ms |
| Exclude one Bronx row (incremental) | 67–76 ms | 65–72 ms |
| Exclude a whole 54-row group | 4–5 ms | 4 ms |
| Leave-one-out for the Bronx median (443k rows) | 90–103 ms | 83–84 ms |
| WASM linear memory after all of the above | 1.47 GB | 1.48 GB |

Every run produced the same snapshot hash, the same noise-plan output as
M1–M3 native, and the same first receipt (row 0: unique_key 59889016, a
Bronx loud-music complaint at 00:00:20 on 2024-01-01).

## Against the budgets (restated for 7.1M rows)

The original budgets were written for 5M rows. As decided on 2026-09-25,
the snapshot stays at two years (7.1M rows) and the budgets are restated
from these measurements. The proposal below is for you to confirm:

| Budget | Proposed (7.1M rows) | `mt` measured | `st` measured |
|---|---|---|---|
| Warm load, including verification (ADR 0001: 2 s) | 2 s threaded, 4 s fallback | 1.65–1.80 s ✅ | 3.2–3.6 s ✅ |
| Typical plan (filter, group, aggregate) | 1 s | ≤ 0.69 s ✅ | ≤ 0.88 s ✅ |
| Click a number: trace | 50 ms | ≤ 15 ms ✅ | ≤ 20 ms ✅ |
| What-if: exclude rows | 150 ms | ≤ 72 ms ✅ | ≤ 76 ms ✅ |
| Full-table sort | 3 s | 2.1–2.3 s ✅ | **5.7–5.8 s ❌** |
| Memory | 2 GB | 1.48 GB ✅ | 1.47 GB ✅ |

**Misses and follow-ups:**
- **Full sort on the single-threaded fallback.** A sort followed by a
  `limit` only needs the top k rows, and a top-k path would make this
  plan fast in both builds. This is the same follow-up noted in M1 and M2.
- **Cold load over a real network.** 497 MB uncompressed is too much to
  download (ADR 0001 left compression to be decided in M4). Compression
  depends on the static host chosen in M5 (`Content-Encoding` vs. LZ4 in
  WASM), so it moves to M5.
- **Memory is about 3× the data size.** The input bytes are copied into
  WASM memory, decoded (about 0.5 GB of columns), and WASM memory never
  shrinks. Streaming the decode chunk by chunk (M5) would drop the copy.

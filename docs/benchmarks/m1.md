# M1 benchmarks: plan execution on the real snapshot

**Machine:** the same cloud container as the M0 real-data run: 4 vCPU Intel
Xeon @ 2.1 GHz, 15 GB RAM, native release build, single-threaded. This is
not the browser/WASM target the spec's budgets refer to (that's M4). These
numbers are a native baseline.

**Data:** NYC 311 snapshot `3b42e46a…` (7,111,809 rows), plus its first
5,000,000 rows (the size the budgets are stated for).

**Harness:** `cargo run --release -p receipts-bench --bin m1 -- <snapshot dir>`.
Each plan runs 5 times. Times cover `execute` only (validation takes
microseconds). Loading and verifying the snapshot took 7.4 s, and peak RSS
for the whole run was 1.58 GB (the verify pass and the loaded table are both
in memory).

| Plan | 7.1M rows (median) | 5M prefix (median) | Output rows |
|---|---|---|---|
| Filter one complaint type, count | 207 ms | 154 ms | 1 |
| Known issue: closed before created, count | 127 ms | 98 ms | 1 |
| Noise: median hours to close by borough (filter, map, group, median, sort) | 585 ms | 423 ms | 6 |
| Top complaint types per month in 2025 (filter, `date_trunc`, 2-key group, sort, limit) | 507 ms | 225 ms | 10 |
| All rows: map + group by agency × status (count, count_non_null, max) | 361 ms | 297 ms | 48 |
| Full sort by closed_date desc, unique_key asc, first 10 | 2,260 ms | 1,691 ms | 10 |

## Cross-checks against M0

Computed by the engine, independently of the snapshot builder:

- `closed_date < created_date`: **1,904** rows, equal to the manifest's
  `KI-closed-before-created`.
- `created_date >= 2025-01-01`: **3,655,040** rows, equal to the Socrata
  API's own `count(*)` for 2025.
- `complaint_type = "Noise - Residential"`: 842,645 rows.

## What the time goes to

These are first implementations, written for clarity, and verified against
the reference interpreter. They are not tuned yet:

- **Expressions** evaluate through a boxed per-row accessor and build
  `Vec<Option<_>>` before packing bitmaps. A dictionary-code filter over
  7.1M rows should take about 10–20 ms, not 200 ms. Typed kernels for the
  common shapes (column vs constant, dictionary codes) are the obvious next
  step.
- **Sort** is a comparison sort with a boxed comparator per key (about 23
  comparisons per row). A radix or key-normalized sort, or a top-k heap
  when a `limit` follows, would cut this sharply. The "first 10 by
  closed_date" plan only needs top-k.
- **Filters copy** the surviving rows of every column. A selection vector
  would defer that.

None of this changes semantics or hashes, so it can land any time before
M4 under the same differential test.

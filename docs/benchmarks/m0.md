# M0 benchmarks: snapshot pipeline

**Machine:** cloud container, 4 vCPU Intel Xeon @ 2.8 GHz, 15 GB RAM, Linux,
release build, single-threaded. This is **not** the "mid-range laptop in
Chrome" the spec's budgets refer to. None of the spec's budgets cover the
offline snapshot step. These numbers are a baseline for M4, when loading
moves into the browser.

**Data:** synthetic 311-like records from `receipts-snapshot synth --seed 42`,
because the Socrata API is unreachable from this environment. Records have
the real field set and realistic cardinalities: 250 complaint types, 1,500
descriptors, about 200 ZIPs. Anomalies appear at low rates. The full
two-year size is estimated at 6.7M records.

## Profiling notes

The first version took **81 s**. Timing each stage on 1M records showed that
most of the cost was allocation, not parsing:

| Per 1M records | Time |
|---|---|
| Split page into raw records | 0.56 s |
| … + `serde_json::Map<String, Value>` per record | 2.82 s |
| … + re-serialize each value for the duplicate fingerprint | 4.72 s |
| … + borrowed `(&str, &RawValue)` fields instead | 1.81 s |

Two changes, both keeping the snapshot hash identical:

1. Parse each record into borrowed slices of the raw JSON. Strings without
   escapes are never copied.
2. Compute the duplicate fingerprint as one plain BLAKE3 over a reused buffer
   of raw field text, instead of a keyed hasher with 42 small updates.

This brought `build` from 81 s to 52 s. What's left is interning 9 text
fields per record in std `HashMap` (SipHash), cache-unfriendly gathers
during the final sort, and the unavoidable JSON scan. Time per million rows
rises from 5.2 s at 1M to 7.0 s at 6.7M, which points at memory and cache
effects in sorting and gathering. The next step, if this ever matters, is
parsing pages in parallel with a merge of per-page interners. It doesn't
matter now: this runs offline, once per snapshot.

## Correctness checks run at this size

- `verify` on the 6.7M snapshot: all hashes re-derived from the decoded
  Arrow files, and sort order checked.
- Rebuilding from the same raw directory gives the same `snapshot_hash`
  (`9ad85731…`).
- The independent Python oracle (`tools/oracle/snapshot_oracle.py`) agrees
  on 999,753 rows, 1,901 cleaning-log entries, and 247 rejects at 1M records.
  At 6.7M it runs out of memory (Python objects).
- pyarrow 25 reads `data.arrow` unchanged: `uint32` dictionaries, 64Ki-row
  batches, and our schema metadata.

### Comparison with the synthetic estimates

| | Synthetic estimate | Real |
|---|---|---|
| Rows | 6.7M | **7,111,809** (+6%) |
| B/row | 69.9 | 69.9 |
| Raw directory | 2.8 GB | 3.12 GB |
| `build` | 51.9 s | 24.9 s |
| Cleaning-log entries | 12,918 | 0 |
| Rejects | 1,577 | 0 |

- **Build time.** The 51.9 s figure was measured on a different machine.
  Rebuilding the same synthetic benchmark (`synth --rows 6700000 --seed 42`)
  on this machine took **29.3 s** and reproduced its hash `9ad85731…`. So
  most of the gap is the machine, not the data. On the same machine, real
  data builds ~15% faster than synthetic despite 6% more rows: the real
  records hit no cleaning rule, which takes the whole logging and rejection
  path out of the loop.
- **The real data is much cleaner than the synthetic data.** Socrata
  omits null or empty fields instead of sending `""`, trims text, and
  serializes every timestamp as `YYYY-MM-DDTHH:MM:SS.000`. So CR-02 to
  CR-09, CR-11 and CR-12 never fire. An independent streaming scan of all
  7.1M raw records confirmed this: no duplicate keys, no malformed keys or
  timestamps, no leading or trailing whitespace, no empty strings, no
  half-present or unparseable coordinates. The synthetic generator
  deliberately over-represents anomalies. The rules stay because they are
  what makes this *known* rather than assumed.
- **Timestamps are always `.000`.** CR-11 (non-zero fractional seconds)
  never fires, so the source has whole-second precision.

### One-week smoke test and paging checks

`fetch --from 2024-01-01 --to 2024-01-08 --page-size 5000`: 60,496 records
in 13 pages (11.4 s). This equals the API's `count(*)`, with no `:id` seen
twice. A second fetch with `--page-size 997` (61 pages) returned the same
`:id`s in the same order and built the same `snapshot_hash`
(`e0a8bb1d…`). The Python oracle matched exactly: 60,496 rows, 0 log
entries, 0 rejects.
